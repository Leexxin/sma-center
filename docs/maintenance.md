# 文档维护与发布约定

项目改动必须同步更新文档，不能只在聊天中说明。根目录 `AGENTS.md` 已将本约定纳入后续仓库协作要求；这是协作规则，尚未配置自动判断文档是否过期的 CI。

## 变更与文档对应关系

| 代码或部署改动 | 必须检查的文档 |
| --- | --- |
| package.json、Dockerfile、compose.yaml、deploy/dev.mjs、build.mjs | 手册中的环境要求、启动、安装、升级与端口 |
| server.mjs、totp-auth.mjs、auth-pages.mjs、request-origin.mjs、app/auth.ts | 首次绑定、登录有效期、认证恢复、代理限制与排障 |
| drizzle/、deploy/sqlite-env.mjs、存储或加密逻辑 | 数据目录、迁移、备份恢复与回滚兼容性 |
| SMA 指标、服务发现、凭据处理 | SMA 配置、网络访问、可见指标和故障判断 |
| 页面功能、收藏分类、主题、布局设置 | 使用说明、JSON 备份覆盖范围 |
| 服务器地址、卷、目录、镜像、网络与部署版本 | 手册中的环境信息及 deployment-status.md |
| 新增文档、迁移文档路径 | docs/README.md 及所有入口链接 |

## 每次发布的检查清单

1. 查看 `git status`，保护已有修改，确认本次发布范围。
2. `git fetch origin main`，核对 HEAD、origin/main 及未提交修改。远程有新提交先审查差异，不强推覆盖。
3. 完成代码和对应文档变更。迁移用新增文件，不修改已经执行的 SQL 迁移冒充新迁移。
4. 执行相关测试；代码改动通常执行 `npm test`、`npm run lint`、`npm run build`。原生表单认证改动还应执行浏览器回归。
5. 纯文档变更检查链接、示例、`git diff --check`，不以此宣称应用行为已重新测试。
6. 提交并推送 Git；记录提交号。生产发布前完整备份、保存旧镜像和已部署源码快照。
7. 按手册部署，验证健康检查、实际浏览器操作与数据保留；不要在生产运行测试绑定或恢复命令。
8. 核对服务器源码及容器运行内容；更新部署核对记录，提交记录本次上线结果。文档提交与业务版本号可分开记录，避免自引用提交号。
9. 记录失败项、未执行项、迁移/回滚要求。仅推送代码不代表已上线，仅容器 healthy 不代表全部业务正确。

## 安全与记录规则

- 文档只记录命令和脱敏状态，禁止粘贴实际授权码、种子、Token、Cookie 或备份内容。
- `deployment-status.md` 是带日期的人工核对快照，不表示后续持续同步或定时监控。
- 发布或恢复时使用相同 Compose 配置组合；若使用恢复覆盖文件，后续更新也必须带上它。
- 后续实现 HTTPS 代理、定时备份、告警或 CI 时，必须将“限制/未配置”改为经过验证的实际操作步骤。
